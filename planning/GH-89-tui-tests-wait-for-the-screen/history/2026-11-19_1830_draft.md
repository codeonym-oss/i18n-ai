# The TUI tests fail at random on slow CI runners

## Problem

On Windows and macOS runners a different TUI test fails on each run, with no code change behind it (`main` after
#83 and #85, a release-please update, #86, #80, #81). Each time a test reads a screen before it has finished
drawing: a widget mounted but not yet composed (`No nodes match '.kpi-label' on KpiTile`), or a list not yet rebuilt
after a search. The helpers return as soon as a condition holds (`ended`, `planning`) or after a fixed time
(`pause(0.3)`), and `settle` makes one pass over the screen's messages.

## The change

`tests/support/tui.py` gets `drawn` (every widget on the screen mounted, and a round of messages that mounts or
removes none, within a deadline) and `arrived` (the top screen once it is of a kind, drawn). `settle` ends on
`drawn` and goes round again while a worker is left; `ended`, `planning`, `scripted`, `post`, the run tests'
`showing` and the snapshot fixture end on it too; the tests that waited a fixed time wait with `arrived`.

## Done when

- [ ] The TUI tests pass with every widget composing up to 100 ms late at random (a scratch pytest plugin, not kept).
- [ ] No TUI test waits a fixed time before an assertion.
