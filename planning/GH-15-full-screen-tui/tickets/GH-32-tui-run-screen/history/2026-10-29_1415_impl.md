## Steps

1. **Pin the console's output first.** A test of `RichGenerationProgress` on a recording `Console`, through today's
   methods: the "⊘ ignored …" line, and a "● common.json → fr: written" line per job done.
   → check: `tests/infra/test_console_progress.py` passes on `main`'s code; it is kept, its calls changed to the
   events in step 3, its expected lines unchanged.

2. **The engine tells an atom's start and its retries** (decision 001). `engine.py`: two events in the port,
   `AtomStarted(job)` and `AttemptRejected(job, messages, attempt, attempts)`, in `EngineEvent`. The atom writes them
   with `get_stream_writer()`: `AtomStarted` in `extract`, `AttemptRejected` in `validate` when it leaves rejected
   messages and attempts remain (the test `after_validate` routes on; a node, not the edge, writes) (`messages` = the pending count, `attempt` = the one coming, `attempts` = `max_attempts`). The
   engine streams `["updates", "custom"]` with `subgraphs=True`, yields the custom events from any namespace, and
   the `updates` of the root namespace only, as today.
   → check: an engine test (`tests/infra/test_engine.py`) runs `LangGraphTranslationEngine` with the fake gateway,
   `broken_first={"app.welcome"}`, on i18next's `common.json` into `de`: the events for that job are, in order,
   `AtomStarted`, `AttemptRejected(messages=1, attempt=2, attempts=3)`, `FileTranslated`. The integration suite
   still passes.

3. **The progress port takes typed events** (decision 001). `application/ports/progress/`: the events
   `RunStarted(jobs)`, `JobStarted(file, target)`, `JobRetrying(file, target, messages, attempt, attempts)`,
   `JobDone(result: FileResult)`, `FileDropped(file, jobs, reason)`, `RunFinished()`, a `ProgressEvent` union, and
   `IGenerationProgress.on(event)`. The handler sends them where it called `start`, `drop`, `advance` and `finish`,
   and turns `AtomStarted` / `AttemptRejected` into `JobStarted` / `JobRetrying`. `RichGenerationProgress` renders
   `RunStarted`, `FileDropped`, `JobDone`, `RunFinished` as today and ignores the rest; its status colour comes from
   `result.status` instead of parsing a string. `SilentProgress` and `RecordingProgress` follow.
   → check: step 1's test, unchanged lines; `tests/test_bootstrap.py` sees `RunStarted(3)` … `RunFinished()`, and,
   with `broken_first`, a `JobRetrying`; the CLI suite passes as it is.

4. **The grid, shared** (decision 002). `cli/tui/grid.py`: `JobGrid(DataTable)`, built from the `ScanReport`'s
   qualified files and targets, with `show(file, locale, text)`; `PlanScreen` uses it for its cells (its labels,
   toggles and keys unchanged).
   → check: the plan's Pilot tests pass unchanged.

5. **The run screen, live** (decision 002). `TuiProgress` posts one `TuiProgress.Event(event)` message;
   `RunScreen(report, plan)` shows a `JobGrid` whose cells start **waiting**, or **off** for the plan's cells off,
   and follow the events: `JobStarted` → **translating**, `JobRetrying` → **retry k/n**, `JobDone` → **written**,
   **partial**, **failed** (or **refused**, never in the TUI), `FileDropped` → **ignored** across its row; a
   `ProgressBar` from `RunStarted` and `JobDone`/`FileDropped`; **Problems**, a `Log` with a line for each failed
   or partial job (its reason, or how many messages kept their source). At the end the receipt and "To run it
   again" replace the grid (the problems stay). `setup.py` passes the report and the plan to `RunScreen`.
   → check: Pilot tests: a run's cells end written; with `broken_first`, a cell reads "retry 2/3" before it reads
   "written" (record the cell's texts as the events arrive); a `Stubborn` run lists the partial file under
   Problems; a cell off in the plan reads "off" on the run screen. The existing run tests are updated for the grid
   (no `#jobs` line count).

6. **Docs.** Getting started's run paragraph: the live grid, retries, the problems; a run screenshot is not added
   (a live state is hard to catch; the plan's shows the grid).
   → check: `uv run --frozen sphinx-build -W --keep-going -b dirhtml docs docs/_build/html`.

7. **Everything.** `uv run --frozen ruff check . && uv run --frozen ruff format --check .`, `uv run --frozen mypy`,
   `uv run --frozen lint-imports`, `uv run --frozen pytest` (coverage ≥ 85 %), and `i18n-ai generate` on a copy of
   an example with the fake model in a pty, to see the console's lines are as before.

## Risks

- **`subgraphs=True` changes the stream's items** to `(namespace, mode, chunk)`: the engine must take `updates`
  from the root namespace only, or the atoms' own node updates come through as events. Step 2's test and the
  integration suite cover it.
- **The console's output** must not move: step 1 pins it before the port changes.
- **Every progress implementation changes** (console, TUI, the fakes' `SilentProgress`, the tests'
  `RecordingProgress`); mypy strict finds the ones left.
- **A retry test that depends on timing:** the Pilot test records the cell's texts as events arrive instead of
  sampling the screen.

## Corrections while building (2026-10-29)

- **Where the events live:** in `generate_locales/progress.py`, beside the receipt whose `FileResult` `JobDone`
  carries, exported with the command; `IGenerationProgress.on` names `ProgressEvent` under `TYPE_CHECKING`, since
  the port importing the command package at run time would be an import cycle (the handler imports the port).
- **`Planned` keeps its cells `off`:** the run screen shows them as "off" without rebuilding them from the escaped
  `exclude` patterns.
- **Step 2 alone** has the handler skip the two new engine events; step 3 turns them into progress events.
